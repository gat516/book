# QiReadr deployed inference baseline — September 22, 2026

The bounded production run found no slowdown attributable to chapter contention and
no observed provider-limit errors. It does **not** justify adding gateway admission
to the current hosted setup. Reported output-token volume is the more promising
optimization lead: its correlation with request latency was **0.997689** in this run.
This is an exploratory association, not a causal experiment on reasoning settings.

## Method and evidence

- Window: **22:26:30–22:30:50 UTC**, September 22, 2026. The earlier 19.481-second
  pilot was excluded from this comparison.
- Existing AWS/k3s deployment: two pipeline replicas, one chapter at a time for the
  measured account; Ask AI/pipeline image `python:ebd1d43`.
- A sequential HTTP client called the **running Ask AI service**, using internal
  authentication and account identity. Its chapter gate was checked against saved
  progress. No mock providers, replacement images or gateway were introduced.
- End-to-end **service** time includes retrieval and completion, but excludes the
  browser, Cloudflare, reader API and its separate admission limiter.
- Redis active stages were sampled every 0.5 seconds. Four requests had 100% observed
  chapter overlap and one had 50%. Stages included translate, display scan, facts and
  chunk indexing. Stage overlap is not an exact measurement of simultaneous upstream
  model requests, although the successful pipeline calls confirm real provider work.
- Starts were spaced at least seven seconds apart. The owner approved at most 24
  additional requests and one chapter; the run used 17 because processing finished
  before the maximum overlap sample count was reached.
- Fixed request/context controls reduce some variation but also warm provider caches.
  The provider returns a model-family identity rather than an immutable model build.
  Neither cache-hit detail nor provider internal scheduling was measured.
- One book, one question, one chapter and sequential arrivals are a **screening
  baseline**, not a saturation test or a defensible p95/p99 benchmark. Differences
  among the phase medians must not be marketed as an optimization win.

## Next optimization experiment — not run

The deployed Ask AI call (`services/askai/askai/app.py` at `ebd1d43`, line 305)
does not pass `reasoning_effort` or a per-request output budget. Its hosted adapter
defaults to 8,192 output tokens. DeepSeek's current documentation says thinking is
enabled by default at high effort and supports lower effort or disabling thinking.
See [DeepSeek thinking-mode documentation](https://api-docs.deepseek.com/guides/thinking_mode/)
(checked September 22, 2026). This makes excessive reasoning a plausible explanation
for the variable reported output and a better next hypothesis than shared admission;
the current measurement did not explicitly record or vary reasoning effort.

For project-quality improvement metrics, compare the current Ask AI settings against
explicit low effort (and, separately, non-thinking for simple lookup questions), with
the same provider, context limits and spoiler gates. Use a representative fixed
question set, alternate baseline/variant order across repeated runs, and preserve a
holdout set. Record reasoning/visible token counts separately where available.

Predeclare success in terms of **median/p95 latency and token usage**, with enough
samples and uncertainty estimates, while preserving answer support, citation accuracy,
chapter authorization and background throughput. Do not trade silent truncation or
weaker answers for a latency headline. Deploy no new default until that quality check
passes. A gateway performance claim would need a separately labeled, demonstrably
quota-bound workload; this production run did not show that condition.
